# PerchRemote 远控流畅度优化开发文档

## 文档目标

围绕窗口拖动、滚动和连续动画时的卡顿，建立可复现的测量方法，识别延迟所在阶段，再实施有数据依据的优化。项目已经具备 WebRTC 视频传输、分离的控制与鼠标移动通道、原生桌面采集、共享纹理、帧率和画质控制，以及基础网络诊断。本方案在这些能力上迭代。实施记录更新于 2026 年 11 月 24 日。

本轮交付目标包括以下四项。

1. 能区分采集、编码、网络、解码、显示和输入注入各阶段的问题。
2. 能在 macOS、Windows、直连和 TURN 中继条件下复现并比较窗口拖动体验。
3. 优化后维持键鼠按下、松开和快捷键的可靠性，并使视频帧队列保持有界。
4. 根据实测确定后续的码率、分辨率、帧率和采集优化优先级。

## 优化前实现基线

### 视频采集与发送

- macOS 使用 ScreenCaptureKit 采集 BGRA 帧，通过 IOSurface 和 Electron `sharedTexture` 交给渲染进程，再由 `MediaStreamTrackGenerator` 生成视频轨道。
- Windows 使用 Windows Graphics Capture 与 D3D11 共享纹理，再交给同一 Electron 视频轨道管线。
- 采集端已有在途帧约束。主进程只允许一个帧在 `sendSharedTexture` 中处理，并限制保留纹理数量。预加载脚本在 `writer.desiredSize` 不足时跳过帧。忙碌期间到达的新帧会被直接丢弃，连续变化结束时可能遗漏末尾更新。
- 视频轨道设置 `contentHint = 'motion'`。发送端配置帧率上限、码率上限、分辨率上限和 `maintain-framerate` 降级偏好。
- 目前画质档包括 720p、1080p、1440p 和 4K，帧率选项包括 30、60、90 和 144 fps。配置值是上限，实际帧率还受采集源、编码负载和网络影响。
- 视频由 Electron 内置 WebRTC 编码与发送。H.264/H.265 是当前可选偏好，偏好协商结果不直接表示具体硬件编码器型号。

### 输入发送与注入

- 主控端按 `requestAnimationFrame` 合并鼠标移动事件。
- 双方使用新版控制协议时，鼠标移动和拖动坐标通过无序、零重传的 `motion` DataChannel 发送。按键、鼠标按下与松开、滚轮等控制消息通过有序可靠的 `control` DataChannel 发送。旧版协商保留既有控制通道行为。
- 控制消息带有序号和控制授权 epoch。拖动坐标携带可靠按钮事件的屏障序号，被控端按屏障校验后再注入。
- 被控端校验坐标、消息类型和速率，再经 Electron IPC 交给 macOS 或 Windows 原生输入模块。

### 优化前可见诊断

`Peer.diagnostics()` 读取 WebRTC `getStats()`，工作台约每 900 ms 更新一次连接路径、当前 RTT、视频码率、协商编码、实际视频尺寸和发送帧率。当前值适合连接状态观察，尚不能单独定位拖动卡顿的阶段，也没有持续记录 p50/p95、帧丢失或视频冻结情况。

项目 README 已记录对本机 UU 远程 macOS 二进制的符号检查，发现其包含 WebRTC/ICE 会话协商相关符号。这为两款产品共享 WebRTC/ICE 技术背景提供了项目内的直接观察。完整媒体链路、调度策略和具体参数仍需要实测或进一步验证。

## 原始技术说法审查

| 说法 | 工程判断 |
| --- | --- |
| WebRTC 能实现流畅窗口拖动 | 具备实现低延迟远程桌面的基础能力，实际体验取决于采集、编解码、队列、网络和显示全链路 |
| ICE 自动保证 P2P 与 60 ms 内延迟 | ICE 的结果受 NAT、网络和 TURN 配置影响。延迟需要注明测量边界、设备和路径 |
| UDP 与 DataChannel 消除所有阻塞 | 媒体和数据仍受带宽、拥塞、缓冲与丢包影响。无序、部分可靠通道适合可替换坐标，按钮边沿需要可靠状态语义 |
| 默认自带 QSV/NVENC 硬编码 | 硬件加速取决于 Electron/Chromium 构建、驱动、硬件和编码格式。协商编码与硬件编码器能力需分别验证 |
| 只发送脏矩形即可优化标准视频流 | OS 变化检测与编码器更新区域需要配套设计。当前项目传输完整视频帧，共享纹理和编码器可复用相关平台优化 |
| 独立 DataChannel 自动获得最高优先级 | 通道拆分有助于表达可靠性与合并语义，实际调度和背压仍需测量 |
| 关闭过载检测、缩短 I 帧间隔必然更流畅 | 编码负载和关键帧码率峰值会影响延迟，应逐项实验并观察限制原因 |
| requestVideoFrameCallback 能直接移除一帧缓冲 | 该 API 提供视频帧观测时机。PerchRemote 已直接显示 video，本轮用它统计呈现间隔 |
| UU 远程完整媒体链路基于某种改良版 WebRTC | 项目 README 记录的二进制符号观察支持其包含 WebRTC/ICE 相关能力。完整媒体链路及性能排名需要进一步证据 |

## 本轮实施记录

### 已实现的链路修复

1. 原生采集帧率跟随设置。macOS 动态更新 ScreenCaptureKit 的最小帧间隔，Windows 调整捕获轮询周期。默认 60 Hz，支持 30/60/90/144 Hz。Windows 在有限帧池内选取最新可用帧。
2. 共享纹理交接保留一个最新待处理帧。交接忙碌或两个纹理引用尚在使用时，新帧覆盖旧待处理帧。发送结束、纹理引用释放时自动继续交接，覆盖末尾画面更新场景。主进程最多持有两个已导入纹理和一个待处理原生帧，停止时释放待处理帧。
3. 输入屏障恢复。鼠标坐标先于可靠按钮事件到达时，暂存最新坐标，在匹配屏障到达后依序分发。授权 epoch、过期序号和 reset 参与校验。
4. 通道背压恢复。主控端仅保留一个最新待发送坐标，在 bufferedamountlow 到达时重试。按钮、按键和 reset 会清除待发送坐标，避免跨状态重放。
5. 输入速率分配。移动和滚轮使用单独额度，可靠键鼠状态使用另一份额度。松开事件与 reset 保留释放路径。两份额度的容量均为 240，每秒补充 180。
6. 采集生命周期处理。写入失败会触发会话清理，已停止采集的异步写入结果按所属采集实例处理。纹理、VideoFrame 和原生引用分别释放。

新增 `desktop/screen-pipeline.cjs` 承接原有采集交接函数，便于直接验证忙碌、引用保留和停止时的行为。`desktop/input-flow.cjs` 承接输入校验、分配额度与分发。打包清单已包含这两个模块。

### 分阶段诊断与导出

在主控控制中心的「更多 → 导出性能诊断」保存 JSON。页面也提供只读 `window.perchPerformanceSummary()` 快照，供基准脚本读取。

| 阶段 | 已记录的数据 |
| --- | --- |
| 原生采集 | 目标 fps、回调数量与间隔、忙碌/引用限制延后次数、待处理帧替换次数、在途引用和待处理数量 |
| macOS 帧年龄 | ScreenCaptureKit 样本 PTS 到 JS 回调的年龄，使用宿主时钟计算 |
| 纹理与轨道 | 最新帧等待时间、共享纹理发送耗时、轨道写入耗时、writer 背压与写入错误 |
| 编码与网络 | 实际编码、尺寸、fps、码率、编码均时、编码限制原因、可用发送带宽、选定路径、RTT、重传 |
| 接收与解码 | 丢包、jitter、按区间计算的抖动缓冲均时、解码均时、丢帧、冻结次数与累计时长 |
| 呈现 | requestVideoFrameCallback 观测间隔 p50/p95/max、回调数量和回调跳过计数 |
| 输入 | 发送、合并、背压、过期、屏障暂存及恢复计数，分发回执 RTT 与本机分发耗时 p50/p95/max |

WebRTC 均时使用累计耗时差除以区间帧数。统计对象 ID 改变、时间戳重复或倒退、计数器重置时重新建立采样基准。运行时缺少的字段在 JSON 中省略。macOS 样本年龄、交接和轨道耗时提供累计均值所需计数及最大值，呈现和输入分布使用滚动样本。

诊断采样约每 900 ms 一次，同一连接每次仅进行一轮采样。双方协商 `performance = 1` 后，被控端通过控制通道发送精简阶段数据。主控端接收、校验并附带数据年龄，超过三秒的被控数据等待刷新。路径重建会重新建立呈现基准。

历史最多保留 600 个阶段采样、600 个呈现间隔和 256 个输入回执。输入探针发送上限约 4 次/秒，主控与 Windows 帮助进程分别保留最多 16 个待确认回执。摘要内容为性能计数、配置和运行时信息。回执阶段标记为 `native-dispatch-return`，表示 macOS 原生调用返回或 Windows 帮助进程完成 `apply` 调用。目标应用处理输入、屏幕刷新和显示器扫描仍需桌面实测核验。

### 可重复基准

`test/performance.mjs` 通过正式邀请、允许观看、画质设置和媒体播放入口建立真实 WebRTC 会话。画面源使用移动窗口、文本行和时间水印组成的确定性 canvas 动画。接收端约每 100 ms 读取一次水印，记录同一台机器上的合成源到视频观测时刻的延迟。

默认源为 1280 × 720、60 fps，预热三秒后采样六秒，重复三轮。基准记录解码尺寸变化、回调遗漏、帧间隔分布和合成源延迟分布。WebRTC 的启动带宽自适应在本次采样中使用了 320 × 180、480 × 270、640 × 360 和 960 × 540，结果按实际解码尺寸解释。

```sh
npm run test:performance
PERF_OUTPUT=/tmp/perch-performance.json npm run test:performance
PERF_WIDTH=1920 PERF_HEIGHT=1080 PERF_FPS=60 PERF_DURATION_MS=10000 npm run test:performance
PERF_FPS=30 PERF_REPEATS=3 npm run test:performance
```

可设置 `CHROME_BIN` 选择 Chromium。对应用层集成做配对比较时，先保存待比较版本的 `public/app.js`，再用 `PERF_APP_SOURCE` 指向该快照运行同一脚本。该方式共用当前仓库的其他模块，适合比较应用层集成开销。完整版本与原生路径的比较需使用相应版本的完整构建。

## 性能问题模型

远控画面更新经过以下链路。

```text
屏幕变化
  → OS 屏幕采集
  → 共享纹理交接
  → 视频轨道与编码
  → ICE 选定路径和网络传输
  → 接收端抖动缓冲与解码
  → 视频元素合成显示

鼠标或键盘事件
  → 浏览器事件合并
  → DataChannel
  → 被控端校验
  → IPC 与原生输入注入
  → 被控屏幕变化
```

用户感受到的拖动跟手程度同时受输入往返和画面反馈影响。仅看 RTT 或发送端 FPS，无法确认画面何时显示，也无法区分编码器过载、接收端丢帧和采集帧排队。

WebRTC 为媒体和数据提供传输与拥塞控制机制。当前工程应把性能结论建立在端到端测量上。SRTP/ICE、DataChannel 的可靠性与有序模式、不同端点的编解码及硬件加速支持都应按实际会话验证。[RFC 8835](https://www.rfc-editor.org/rfc/rfc8835.html) · [RFC 8831](https://www.rfc-editor.org/rfc/rfc8831.html) · [RFC 8836](https://www.rfc-editor.org/rfc/rfc8836.html)

## 后续实验设计

### 阶段一，建立可观测性

先扩展现有 `getStats()` 采集和原生采集计数，形成一份可导出的本机会话摘要。每个指标注明采样时间、单位、发送端或接收端来源。缺少浏览器支持的字段以空值呈现，不伪造为零。

| 阶段 | 建议记录的指标 | 用途 |
| --- | --- | --- |
| 采集 | 回调帧数、帧间隔、共享纹理交接耗时、忙碌跳帧数、背压跳帧数、尺寸变化 | 识别采集不稳定和交接队列压力 |
| 编码 | `framesEncoded`、`totalEncodeTime`、实际帧率、编码尺寸、`qualityLimitationReason`、可用时的目标码率 | 区分编码负载与带宽约束 |
| 发送网络 | 选中 candidate pair、直连或 TURN、RTT、发送字节、重传和丢包相关统计、可用时的 `availableOutgoingBitrate` | 识别路径变化、网络拥塞和重传压力 |
| 接收网络 | `packetsLost`、jitter、`jitterBufferDelay`、`jitterBufferEmittedCount` | 判断接收缓冲等待和丢包情况 |
| 解码与显示 | `framesDecoded`、`framesDropped`、`totalDecodeTime`、冻结次数与时长、视频帧呈现间隔 | 判断解码和合成显示是否跟不上 |
| 输入 | 主控事件到发送耗时、DataChannel `bufferedAmount`、被控端消息接收和原生注入耗时、被控端确认耗时 | 把输入通道排队与屏幕反馈分开观察 |

实现要点包括以下内容。

- 扩展 `public/session.js` 的 `diagnostics()`，按发送端和接收端分别读取统计项。保留已有路径、RTT、码率、编码和分辨率字段，保持调用方兼容。
- 在 `desktop/main.cjs` 和 `desktop/preload.cjs` 的现有帧交接位置增加轻量计数。区分采集未产生新帧、发送仍忙、纹理保留达到上限和视频轨道背压。
- 在 `public/app.js` 中增加调试摘要入口。常规网络浮层保持精简，调试信息按用户主动打开后显示。
- 对显示阶段使用 `<video>` 的 `requestVideoFrameCallback` 采集呈现间隔和 missed-frame 计数。视频仍由原生视频元素直接播放，调试阶段不额外引入 canvas 拷贝。
- 对输入注入增加序号级阶段耗时。若需要确认原生注入完成时刻，为 IPC/原生模块添加带序号的完成回执。回执用于诊断，不改变键鼠消息的排序和授权校验。
- 统计摘要仅保存在当前运行会话的有界内存环形缓冲区。默认不记录屏幕帧、键盘内容、文件内容、邀请密钥或账号凭证。
- 浏览器统计字段按能力检测读取。`totalEncodeTime`、冻结统计、目标码率等字段在各运行时的可用性可能不同。

### 阶段二，形成基准测试

固定版本、主控和被控设备、显示器刷新率、屏幕分辨率、系统电源状态和网络条件。每种场景重复运行，保存统计摘要和运行说明。

| 测试维度 | 场景 |
| --- | --- |
| 活动画面 | 拖动普通窗口、连续滚动长文档、快速切换窗口、静态桌面后短促拖动 |
| 画质档 | 720p60、1080p60、1440p60，以及 90/144 fps 高刷条件 |
| 连接路径 | 同网段 P2P、跨网 P2P、强制 TURN 中继 |
| 设备组合 | macOS 被控与主控、Windows 被控与主控、跨平台组合 |
| 系统负载 | 空闲、编码负载偏高、网络带宽受限或抖动 |

测试过程应同时记录视频显示帧间隔、冻结时间、编码限制原因、实际编码尺寸、RTT、jitter、丢包、输入消息到达和注入耗时。通过同一脚本播放或拖动可重复的窗口内容，减少人工操作差异。输入到显示的整体延迟可用高帧率外部摄像记录屏幕和主控输入指示，作为跨设备时钟难以统一时的端到端核验方法。

每次候选变更与基线做同设备、同网络的配对比较。目标值从第一轮基准结果确定，记录 p50、p95、最大值、丢帧比例和冻结时长。性能优化验收同时检查键鼠按下/松开可靠性、文件传输、TURN 切换、旧版协商兼容和安全停止快捷键。

### 阶段三，优化帧队列和交接

基于阶段一数据判断采集端是否产生排队，以及目前的主动跳帧是否足够。

- 保持共享纹理路径，优先验证现有单帧发送锁、最多两个保留纹理和 `writer.desiredSize` 背压是否在各平台一致生效。
- 为每个跳帧原因单独计数。若 `sending` 或 `retained` 丢弃率高，检查 `sendSharedTexture` 完成时间、渲染进程写入速度和轨道背压，再决定是否调整在途帧限制。
- 保持“最新可用帧优先”的低队列目标。只有实测显示帧到达稀疏且队列空闲时，才测试增大在途帧数。任何增加都必须比较画面更新率和拖动延迟。
- macOS 单独测量 ScreenCaptureKit 回调、IOSurface 引用释放和共享纹理交接。Windows 单独测量 Graphics Capture 帧获取、D3D11 `CopyResource`、共享句柄和 Electron 导入耗时。
- 用实测对比 `contentHint` 的 `motion`、`detail` 和可用的 `text` 场景。窗口拖动关注帧率和动态区域，文档场景关注文字清晰度，选择结果依据画质与延迟数据。
- 将变化区域/脏矩形采集列入独立专项评估，验证 OS API、编码器和跨平台维护成本后再决定是否进入主链路。当前 ScreenCaptureKit 与 Windows Graphics Capture 已提供原生帧源，先测量现有共享纹理与编码链路。

### 阶段四，基于瓶颈做视频自适应

现有控制中心是用户设置上限，发送端使用 `maxBitrate`、`maxFramerate`、分辨率上限和 `maintain-framerate`。自动自适应应与这套手动配置共存。

- 首先读取 `qualityLimitationReason`、实际编码帧率、编码耗时、可用发送码率、接收端抖动缓冲和显示冻结统计。
- 带宽受限时，优先在用户允许的画质范围内调整分辨率与码率。CPU 或 GPU 编码受限时，按实测调整分辨率、帧率或编码器能力。
- 控制器采用滞回区间和最短保持时间，避免网络状态在阈值附近时频繁切档。每次变更记录触发指标、旧配置、新配置和恢复条件。
- 用户明确选择的画质档和帧率作为上限。自动策略只在该上限以内调节，并在控制中心显示当前自动调整状态与实测值。
- 编码器过载检测关闭、GOP 长度或关键帧间隔调整属于单独实验变量。每次仅改变一个因素，记录码率峰值、编码耗时、冻结和恢复时间。
- H.264/H.265 协商结果、编码耗时、实际帧率和硬件编码器使用情况按操作系统及设备分别验证。

### 阶段五，按指标优化输入反馈

现有 `motion` 与 `control` 两通道已经分别承载高频坐标和可靠状态事件。先通过序号级耗时确认瓶颈，再调整队列或发送策略。

- 统计 `motion` 通道背压与合并次数、拖动期间实际发送频率，以及被控端因屏障延迟而暂存和恢复的移动消息。
- 统计控制通道 `bufferedAmount`、按钮和按键消息的端到端确认耗时。按钮松开与 reset 继续使用可靠路径。
- 若 `motion` 消息排队，优先合并旧坐标并保留最新坐标。移动位置属于可合并状态，按钮边沿、按键边沿和 reset 继续保留可靠语义。
- 测试 60/90/144 Hz 主控刷新率下，`requestAnimationFrame` 事件合并和被控端速率令牌是否造成移动坐标间隔异常。
- DataChannel 优先级只作为具体运行时的可选优化。先验证目标 Electron 版本的 API 暴露、SCTP 调度和弱网表现，再决定是否引入。

## 验收与回归

### 性能验收

- 对基线场景生成会话摘要，至少包含平台、Electron/Chromium版本、画质档、帧率上限、连接路径和统计字段可用性。
- 对窗口拖动场景给出接收端显示帧率分布、帧间隔 p50/p95、冻结次数/时长、输入注入耗时 p50/p95。
- 对直连和 TURN 分别完成测试，并保存实际 ICE 路径、RTT、丢包、jitter 和接收缓冲统计。
- 优化项需能在同条件重复测试中改善目标指标，且键鼠可靠性、画面尺寸、音频、文件互传和资源占用处于已约定范围。
- 当统计字段不可用时，提供基于本地计时器的阶段数据或记录为不可测，并注明测量边界。
